## Start from movement, not sections

Structure the content around the change the audience must experience. Do not begin from conventional headings such as introduction, problem, solution, benefits, best practices, and conclusion.

Ask:

```text
What does the audience believe, know, or do at the start?
What tension makes the current state insufficient?
What mechanism or sequence resolves the tension?
What evidence makes the resolution credible?
What limitation prevents overclaiming?
What decision or action follows?
```

## Argument graph

Use this default for belief-changing content:

```text
prior belief
-> observation or contradiction
-> mechanism
-> evidence
-> objection
-> limitation
-> implication
-> decision
```

Not every artifact needs every node. Keep only the nodes that advance understanding.

## Instruction graph

Use this for tutorials and how-to content:

```text
starting state
-> target result
-> prerequisites
-> first observable success
-> complete sequence
-> verification
-> likely failures
-> recovery
-> next capability
```

Optimize for successful execution, not rhetorical surprise.

## Decision graph

Use this for comparisons and recommendations:

```text
decision
-> criteria
-> relevant options
-> mechanisms and tradeoffs
-> constraints
-> boundary cases
-> recommendation by condition
```

Do not declare one universal winner when the decision depends on constraints.

## Persuasion graph

Use this for websites, pitches, and launch material:

```text
audience need
-> specific promise
-> how it works
-> proof
-> objection
-> tradeoff
-> action
```

Proof must be adjacent to the claim it supports.

## Section or unit jobs

Assign one primary job to every unit:

- Establish context the audience needs
- State a claim
- Show evidence
- Explain a mechanism
- Demonstrate a task
- Contrast alternatives
- Surface an objection
- Narrow a claim
- Create participation
- Resolve a tension
- Prompt a decision

Delete units whose only job is:

- Announce what comes next
- Restate what came before
- Make the work feel complete
- Add a generic industry observation
- Decorate a slide or page
- Create a list because lists look organized

## Openings

Start with one of these when appropriate:

- A concrete event
- An observable failure
- A precise claim
- A contradiction
- A decision with stakes
- A task the audience needs to complete
- A short scene that earns the larger idea

Avoid:

- General statements about a rapidly changing world
- Topic announcements
- Definitions the audience already knows
- Generic greetings in written content
- Long biography before relevance is established
- "Imagine a world where"

## Examples and stories

Use an example when it performs a job:

```text
prove a claim
make a mechanism visible
show a failure mode
create a decision
reveal a tradeoff
make an abstraction memorable
```

Do not invent examples that sound real. Label composites and hypotheticals clearly.

Use stories only when the events change the argument. Do not add a personal anecdote because talks are expected to have one.

## Mechanisms

When a draft says something happens, ask how.

Weak:

```text
More choices create friction.
```

Stronger:

```text
Each deployment choice forces a new comparison before the developer has seen a successful result. The product asks for judgment before it has earned context.
```

Mechanisms make claims useful and reduce reliance on adjectives.

## Objections and limitations

Represent the strongest reasonable objection, not a weak strawman.

Use limitations to increase precision:

```text
This applies when...
This does not solve...
The recommendation changes if...
The evidence is limited by...
```

Do not add a ritual "challenges" section when no meaningful limitation exists.

## Endings

Choose an ending job:

- Resolve the opening tension
- Reframe the audience's next decision
- Show the final consequence
- Give a concrete next action
- Return to an earlier image with new meaning
- Leave a precise unresolved question

Do not summarize every point unless retention requirements make a recap necessary.

A memorable ending should be earned by the preceding evidence. Do not inflate the language in the final paragraph merely because it is the ending.
